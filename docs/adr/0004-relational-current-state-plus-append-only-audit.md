# 采用关系型当前态加追加式审计

## Context

系统既需要高效查询计划、订单、持仓、任务和风险的当前状态，也需要完整追踪用户消息、Agent 运行、工具调用、风险裁决、成交、保护与学习证据。全量 Event Sourcing 可以从事件重建所有状态，但会显著增加投影、版本演进、查询和运维复杂度；只保存可变关系表又无法满足不可抵赖审计和重放要求。

## Decision

使用规范化关系表保存业务当前态，并在同一数据库事务中追加不可变 `domain_event`、`command_log`、关键 `tool_call` 记录和 outbox。事件包含版本、聚合序列、correlation、causation、幂等键和来源引用；历史纠错通过追加更正或 supersede 事件完成，不原地删除审计事实。订单、成交、账本、保护和学习链必须可从事件与固定输入重放核对，但系统不要求所有查询模型都只能由事件投影生成。

## Consequences

- 常规产品查询保持直接，关键业务链仍可审计、对账和故障恢复。
- 当前态、事件和 outbox 必须原子提交，并持续验证投影与审计链一致性。
- schema 与事件版本需要独立演进策略；事件载荷一旦发布不得进行破坏性改写。
- 该方案不是完整 Event Sourcing，不能假设任意历史当前态都可仅靠事件自动恢复；需要明确哪些聚合承诺可重建。

## Considered Options

- 全量 Event Sourcing：暂不采用，因为新项目首期的复杂度和运维成本高于收益。
- 仅使用可变关系表和普通日志：拒绝，因为无法提供可靠因果链、幂等证据和不可变审计。
