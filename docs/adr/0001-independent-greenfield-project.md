# 建设独立绿地项目，运行时零依赖旧系统

## Context

目标系统是一个全新的 Agent Quant Research & Simulation OS，而不是对 `futures_workflow` 的升级、兼容迁移或替换发布。旧系统包含有价值的算法、测试、数据样本和领域经验，但同时携带脚本边界、SQLite 状态、静态规则与旧执行语义；让新系统在运行时调用旧模块、读取旧库或维持兼容 facade，会把旧约束重新带入目标架构，并造成两个系统之间的真值所有权不清。

## Decision

新系统使用独立仓库、包名、配置、数据库、部署单元和运行生命周期，产品运行时对 `futures_workflow` 保持零依赖：不导入其 Python 包、不调用其 CLI、不读写其数据库，也不通过兼容 facade、双写或旁路调用维持旧行为。可复用资产必须经过逐项审计后复制、重写或抽取为新项目拥有的实现，并按新领域契约重新测试；旧代码、测试、样本和报告只作为来源证据，不成为运行依赖或目标完成状态。

## Consequences

- 新项目可以从第一天采用清晰领域边界和新的交易语义，不需要为旧 schema、CLI 或状态机保留兼容入口。
- “复用”意味着有来源记录的代码/算法移植与重新验收，不意味着两个项目耦合运行。
- 初期可能出现功能暂时少于旧系统、部分代码重复或需要重新实现；这些成本换取独立演进和单一真值所有权。
- 不建设旧库到新库的在线迁移或回滚路径；如需导入历史样本，应使用离线、只读、可重复的数据导入工具，并标记来源和语义限制。

## Considered Options

- 在旧仓库内渐进式重构：拒绝，因为这与“完全新的项目”边界冲突。
- 新项目通过 legacy adapter 运行时复用旧能力：拒绝，因为会保留隐式耦合和双重真值风险。
